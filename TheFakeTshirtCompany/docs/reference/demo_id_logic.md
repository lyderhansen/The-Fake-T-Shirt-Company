# demo_id Application Logic

How `demo_id` is applied across generators. This field is the primary mechanism for filtering scenario-related events in Splunk (`index=fake_tshrt demo_id=exfil`).

## Tagging Patterns

There are two distinct patterns for how generators apply `demo_id`:

| Pattern | Description | Effect on Splunk queries |
|---------|-------------|--------------------------|
| **Injected-only** | Only scenario-specific events (added on top of baseline) get `demo_id`. Baseline traffic during the scenario period has no tag. | `demo_id=X` returns only attack/scenario artifacts |
| **Broad-tagging** | ALL events for a host/source during the affected period get `demo_id`, including baseline traffic that merely experiences degraded performance. | `demo_id=X` returns both scenario artifacts and impacted baseline traffic |

## Per-Generator Breakdown

### Network Generators

| Generator | Sourcetype | Scenarios | Pattern | Scope |
|-----------|-----------|-----------|---------|-------|
| **asa** | `cisco:asa` | exfil, ransomware, firewall_misconfig, certificate_expiry, ddos_attack, cpu_runaway, memory_leak | Injected-only | Scenario classes generate separate ASA events (e.g., `asa_hour()`, `asa_generate_hour()`). Baseline events are never tagged. |
| **meraki** | `meraki:*` | exfil, ransomware, ddos_attack | Injected-only | Scenario events are individually created with `demo_id` parameter. Baseline MX/MR/MS/MV/MT events are not tagged. |
| **catalyst** | `cisco:ios` | exfil, ddos_attack, firewall_misconfig | Injected-only | Scenario events passed with `demo_id` parameter. Baseline syslog events are not tagged. |
| **aci** | `cisco:aci:*` | exfil, ddos_attack, cpu_runaway | Injected-only | Baseline events have `demo_id=""` (empty string). Only scenario-injected faults/events pass a non-empty value. |

### Cloud/Security Generators

| Generator | Sourcetype | Scenarios | Pattern | Scope |
|-----------|-----------|-----------|---------|-------|
| **aws** | `aws:cloudtrail` | exfil, ddos_attack, cpu_runaway, memory_leak | Injected-only | Only attack-specific events (e.g., `GetSecretValue`, `RunInstances` for DDoS, `SetAlarmState`) get tagged. Baseline S3/IAM events are explicitly NOT tagged. |
| **gcp** | `google:gcp:*` | exfil, cpu_runaway | Injected-only | Only specific scenario events (`CreateServiceAccountKey`, `BigQuery export`, `cloudsql.instances.connect` errors) are tagged. |
| **entraid** | `azure:aad:*` | exfil, phishing_test | Injected-only | Sign-in events tagged only for specific exfil users (jessica.brown days 4-14, alex.miller days 5-14). Audit events tagged only when generated by scenario hooks. Baseline sign-ins are not tagged. |
| **secure_access** | `cisco:umbrella:*` | exfil, ransomware | Injected-only | Only scenario-generated DNS/proxy/firewall events get `demo_id`. Baseline lookups are not tagged. |
| **office_audit** | `o365:management:activity` | exfil, phishing_test | Injected-only | Only scenario-specific SharePoint/OneDrive/Teams events are tagged (e.g., alex.miller FileAccessed during exfil staging). Baseline M365 events are not tagged. |

### Collaboration Generators

| Generator | Sourcetype | Scenarios | Pattern | Scope |
|-----------|-----------|-----------|---------|-------|
| **exchange** | `ms:o365:reporting:messagetrace` | exfil, ransomware, phishing_test | Injected-only | Scenario classes generate separate email events via `exchange_hour()`/`exchange_day()`. Baseline email traffic is not tagged. |
| **webex_api** | `cisco:webex:*` | exfil | Injected-only | Scenario-specific meeting/admin/security audit events are tagged individually. Baseline Webex events are not tagged. |

### Infrastructure Generators (Broad-Tagging)

| Generator | Sourcetype | Scenarios | Pattern | Scope |
|-----------|-----------|-----------|---------|-------|
| **access** | `access_combined` | cpu_runaway, memory_leak, firewall_misconfig, dead_letter_pricing, ddos_attack, certificate_expiry | **Broad-tagging** | When a scenario causes `error_rate > 0`, ALL sessions in that hour get `demo_id` -- including normal user sessions that merely experience elevated errors. This is intentional: the scenario degrades the entire web tier, so all traffic is "impacted." |
| **orders** | `retail:orders` | (inherited from access) | **Broad-tagging** | Orders inherit `scenario` from `order_registry.json` (written by access). If the parent web session was tagged, the order is tagged. |
| **perfmon** | `perfmon` | cpu_runaway, ddos_attack | **Broad-tagging** | When scenario is active for a host, ALL perfmon metrics (CPU, memory, disk, network, SQL Server) for that host in that interval are tagged. This is intentional: the scenario affects all system metrics. |
| **linux** | `linux:*` | exfil, memory_leak, disk_filling, ddos_attack | **Broad-tagging** (per-metric) | Each metric type (cpu, vmstat, df, iostat, interfaces) is independently tagged based on whether the scenario affects that specific metric. E.g., memory_leak tags vmstat but not necessarily df. |
| **wineventlog** | `XmlWinEventLog` | exfil, ransomware, phishing_test, cpu_runaway | Injected-only | Scenario classes generate specific security/application events with `demo_id`. Baseline logon/system events are not tagged. Exception: cpu_runaway SQL Server events in Application log are tagged. |
| **sysmon** | `XmlWinEventLog:Sysmon` | exfil, ransomware | Injected-only | Only scenario-generated process creation (EID 1), network connection (EID 3), file create (EID 11), registry (EID 13) events are tagged. Baseline Sysmon noise is not tagged. |
| **mssql** | `mssql:errorlog` | cpu_runaway | Injected-only | Only scenario-generated error log entries (backup stuck, non-yielding scheduler, I/O delays, memory pressure) are tagged. Baseline startup/checkpoint messages are not tagged. |

### Downstream/Correlated Generators

| Generator | Sourcetype | Scenarios | Pattern | Scope |
|-----------|-----------|-----------|---------|-------|
| **servicebus** | `azure:servicebus` | dead_letter_pricing | Injected-only | `demo_id` is set only when `effect["has_effect"]` is true -- i.e., when the scenario actually modifies the event (dead-letter, retry, wrong price). Normal message flow events during the scenario window are NOT tagged. |
| **sap** | `sap:auditlog` | (inherited from orders) | **Broad-tagging** | SAP VA01/VL01N/VF01 events inherit `scenario` from `order_registry.json`. If the parent web order was tagged, all SAP fulfillment events for that order are tagged. |
| **servicenow** | `servicenow:incident` | all 10 scenarios | Injected-only | Scenario-specific incidents/changes are created with `demo_id`. Baseline incidents are not tagged. All lifecycle events (New -> Assigned -> In Progress -> Resolved -> Closed) for a scenario incident carry the same `demo_id`. |
| **catalyst_center** | `cisco:catalyst:*` | cpu_runaway, ddos_attack, memory_leak | Injected-only | `demo_id` is set only on health polls that have scenario-driven `health_override` values. Normal health polls for the same device/site during the scenario period are NOT tagged. |

## SPL Implications

- For attack scenarios (exfil, ransomware, phishing_test): `demo_id=X` returns only true attack artifacts. No false positives.
- For ops/network scenarios (cpu_runaway, memory_leak, etc.): `demo_id=X` on infrastructure generators (access, perfmon, linux) returns ALL traffic during the degradation period, not just the root cause. This is by design -- the scenario affects the entire service.
- To find root cause events only, filter by sourcetype: e.g., `demo_id=cpu_runaway sourcetype="FAKE:mssql:errorlog"` for the SQL errors, or `demo_id=cpu_runaway sourcetype="FAKE:perfmon"` for the degraded metrics.
